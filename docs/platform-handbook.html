01 · Orientation

Overview

Sencecon manages the whole life of a commercial & industrial solar plant: winning the work, delivering the project, commissioning the system, handing it over, and running it. It is two applications talking to one database.

Backend

Sencecon — a .NET 9 Web API in Clean Architecture (Domain / Application / Infrastructure / API), MediatR CQRS, EF Core on PostgreSQL, JWT auth. Repo github.com/philmups15/Sencecon-, default branch main.

Frontend

sensecon-platform — a React 18 + Vite single-page app, no router (screen state in App.jsx), a hand-rolled fetch client, inline styles in the Sencecon teal design system. Repo github.com/philmups15/sensecon-platform, default branch master.

Hosting

One Railway project, sencecon-api, with three services: api, frontend, Postgres. The frontend repo also auto-publishes to GitHub Pages on every push to master.

The shape of a working day

A salesperson logs a lead as an Opportunity and moves it through the pipeline. When it is won, one click converts it into a Project and its first Plant. Delivery teams attach Site surveys, Designs and BOM lines. Once the plant is built, O&M teams raise Work orders, record Commissioning tests, upload the Handover bundle, and track Non-conformities. The customer sees a read-only Portal of their plants and closed work.

03 · Sencecon

The backend

Four projects, dependencies pointing inward. API → Application + Infrastructure → Domain. Domain depends on nothing.

Domain
Entities & enums only. Plant, WorkOrder, Project, Opportunity, Survey, Design, BomItem, NonConformity, CommissioningTestResult, PlantAttachment, User, RolePermission, … plus the lifecycle enums. Base classes carry Id (client-generated GUID) and audit stamps.
Application
Use cases. Commands/ and Queries/ folders per feature, each with a MediatR handler, a DTO, and (for writes) a FluentValidation validator. IApplicationDbContext is the only DB seam. EntityCodeGenerator assigns human codes.
Infrastructure
The outside world. ApplicationDbContext, EF configurations & migrations, JWT generation, password hashing, Resend email, the DB-backed data-protection store. Registered in AddInfrastructure(configuration).
API
HTTP. 15 controllers, all [Authorize]. Each action forwards a request record to ISender and returns the result. ExceptionHandlingMiddleware maps domain exceptions to status codes.

ExceptionHandlingMiddleware wraps the whole pipeline and turns ValidationException → 400, NotFoundException → 404, ForbiddenAccessException → 403, ConflictException → 409, UnauthorizedAccessException → 401, everything else → 500 (logged).

Startup sequence — Program.cs

  1. Build config → register AddApplication() + AddInfrastructure(config).
  2. Configure JWT bearer — validate issuer, audience, lifetime, signing key; OnTokenValidated re-reads the user row and rejects the request if IsActive == false (so "disable user" takes effect immediately).
  3. Register one authorization policy pair {module}-read / {module}-write for every module in ModuleCatalogue.
  4. Build the app. Mount Swagger (all environments).
  5. Run await db.Database.MigrateAsync() — unconditional, on every start.
  6. Exception middleware → HTTPS redirect → CORS → auth → controllers.

04 · sensecon-platform

The frontend

A deliberately small SPA. One App.jsx holds the current screen in state and renders it from a SCREENS map — there is no router, no Redux, no component library.

src/lib/api.js — the whole client

  • Base URL from import.meta.env.VITE_API_URL, default http://localhost:5080.
  • Token in localStorage["sencecon_token"]; attached as Authorization: Bearer on every call.
  • Error handling: non-2xx → throw Error with payload.title or the validation errors.
  • DTO → view mappers (toPlantView, toWorkOrderView, …) translate PascalCase enum strings into the label / tone / key shapes the screens and shared components expect.
  • Permission cache: getRolePermissions() runs once at sign-in; canAccess(role, module, mode) and canViewScreen(role, key) drive the sidebar and every write control. The server enforces the same rules for real.

06 · Who can do what

Authentication & permissions

JWT for identity, a DB-backed matrix for authorisation. Both are enforced server-side; the frontend cache only decides what to show.

Sign-in

  • POST /api/auth/register → creates a User (always role User — there is no first-user-is-admin rule), returns { userId, email, token }.
  • POST /api/auth/login → same shape. Token carries sub, email, jti; lifetime from Jwt:ExpiryMinutes.
  • Admin promotes a user with PUT /api/users/{id}/role, or set Users.Role directly (enum: User 0, Admin 1, ProjectManager 2, Sales 3, DesignEngineer 4).
  • Password reset: admin triggers POST /api/users/{id}/password-reset → Resend emails a 24 h link → public POST /api/auth/reset-password.

The permission matrix

Seeded by migration into RolePermission rows, then editable at Admin › Roles & permissions. Each controller action carries [Authorize(Policy = "{module}-read")] or "{module}-write"; ModulePermissionAuthorizationHandler looks up the row for the caller's role.

07 · Lead to operations

The business flow

The end-to-end path. The one hard automation is the conversion step; everything else is a person choosing a link from a dropdown.

Step by step

  1. Log the opportunity. Customer, capacity, location, owner, value. Move it Qualifying → SiteVisit → Proposal → Negotiation → Won; each move can carry a note and stage-specific free-text fields, and writes an activity-log entry.
  2. Convert (once Won). The button appears only when the stage is Won and it has not been converted; the server re-checks both. It creates:
    • a Project — name "{Customer} – {Location}", stage DesignSurvey, budget = opportunity value;
    • a Plant — same name, capacity carried over, stage DesignSurvey, ProjectId set;
    • an activity-log line: "Converted opportunity to project PRJ-004 and created plant PLT-002".
    The opportunity is flagged Converted (not deleted).
  3. Site survey. From the Surveys screen or from inside the Project. Pick the Project and the Plant (the plant selection auto-fills the site-name field). Status runs Scheduled → … → SignedOff with a manual progress %.
  4. Design. Pick a Project and/or a Survey (a survey without an explicit project inherits its project). Status InReview / Approved, revision string. Code auto-assigned DSN-###.
  5. BOM. Component, quantity, unit cost, supplier, status — each line optionally scoped to the Plant it is installed on.
  6. Advance the plant. Someone sets the plant stage to Deployment, then Commissioning, then Operating. Manual.
  7. Work orders. Raised against a plant (mandatory). Kanban board Open → InProgress → Review → Done; a "Sign off & close" button sets Done.
  8. Commissioning. A fixed checklist — DC (2), AC (2), Monitoring (1), Safety (2). Each test is Pending / Pass / Fail; setting it upserts on (plant, category, testName), recording who and when. Latest value only, no history.
  9. Handover bundle. Versioned file uploads on the plant (re-uploading under the same title bumps the version). Shared by the Plants and Commissioning screens; read-only in the Portal.
  10. Portal. The customer sees their plants (capacity, PR %, health), closed work-order history, and a handover bundle per plant that has documents.
The seam in the middle

The sales/design side (Opportunity → Project → Survey → Design → BOM) and the O&M side (Plant → Work orders → Commissioning → Handover) are joined by exactly one hard link: Plant.ProjectId, created at conversion. Survey → Plant and BomItem → Plant are optional links a person sets. There is still no gated hand-off — no sign-off record, no acceptance date.

Build per service

  • api — multi-stage Dockerfile: sdk:9.0 restores & dotnet publish, aspnet:9.0 runs it. ASPNETCORE_HTTP_PORTS=8080, entrypoint dotnet Sencecon.API.dll. Layer caching makes rebuilds ~40 s.
  • frontend — Nixpacks detects Node, runs npm ci + npm run build, then the railway.json start command npm run start = serve -s dist -l $PORT. VITE_API_URL and VITE_BASE_PATH=/ are baked in at build time.

Migrations on deploy

Program.cs calls db.Database.MigrateAsync() at startup, unconditionally. Every new api container applies pending migrations before it serves traffic — there is no separate migration step. Verified on the last deploy: the three link migrations applied cleanly against the production database.

The deploy procedure

After a PR is merged to the default branch:

Then confirm the deployment reached SUCCESS (railway deployment list) and hit a live endpoint.

GitHub Pages (frontend only)

.github/workflows/deploy.yml triggers on push to master and publishes dist/ to GitHub Pages at philmups15.github.io/sensecon-platform/ — a second, independent copy of the frontend. It does not run on pull requests, so there is no PR check.

No auto-deploy

The api and frontend services have no repo connected, so merging to main/master deploys nothing on its own. Run railway up, or connect the repos in the Railway dashboard for push-to-deploy.

09 · Running it yourself

Local development

PostgreSQL on the host, the API in Development on :5080, Vite on :5173.

  1. Database. PostgreSQL 16 via Homebrew (brew services start postgresql@16), database sencecon_dev, user postgres / postgres, localhost:5432. The API creates the schema on first run via MigrateAsync().
  2. API. 
    ASPNETCORE_ENVIRONMENT=Development \
  dotnet run --project src/Sencecon.API --urls http://localhost:5080
    Swagger UI at http://localhost:5080/swagger. Config comes from appsettings.Development.json (dev connection string, throwaway JWT secret, Frontend:BaseUrl = http://localhost:5173).
  3. Frontend. 
    cd ~/sensecon-platform
npm install
npm run dev   # Vite → http://localhost:5173 (5174 if taken)
    VITE_API_URL is unset locally, so api.js falls back to http://localhost:5080. CORS in appsettings.Development.json already allows http://localhost:5173.
  4. Make an admin. Register through the UI (you get role User), then UPDATE "Users" SET "Role" = 1 WHERE "Email" = '…'; and sign in again for a fresh token.
Two database names

appsettings.json (base) points at a database called sencecon; appsettings.Development.json overrides it to sencecon_dev. Running without ASPNETCORE_ENVIRONMENT=Development locally will try to use sencecon.

11 · Honest edges

Known gaps & stubs

What isn't wired, so nobody trusts a screen that is really a placeholder.

Mock data still on screen

  • Dashboard — entirely mock (KPIs, map pins, stage distribution, activity).
  • Projects — milestones / tasks / subcontractors / risks / budget-line tabs are mock; the project core, surveys and plant panel are real.
  • Surveys — photo-capture grid, measurements and obstructions panels are mock.
  • Design — attachments and revision-history side panels are mock; the field tabs show static values.
  • BOM — "Cost variance vs budget" chart is mock.
  • Reports — the catalogue list is mock; generate / delete are real.

Model gaps

  • No gated handover — no sign-off entity, acceptance date, or certificate; nothing blocks Operating.
  • Commissioning — test list is hard-coded in the frontend, identical for every plant; only the latest result is kept.
  • Non-conformities — full backend CRUD exists but there is no screen; they surface read-only inside Commissioning. The PlantId link can only be set via the API.
  • Design / BOM → upstream — Design.ProjectId and BomItem.PlantId are real columns but the create forms are the only way to set them; there is no bulk backfill.
  • Work orders — no checklist, parts, labour or attachment model; "sign off" only flips the status.
  • Code generation — read-max-then-increment with no row lock; concurrent creates rely on the unique index to fail rather than duplicate.

Operational

  • No CI — the backend repo has no workflows; the frontend's only workflow is the Pages deploy (push to master, not PRs).
  • No push-to-deploy for the Railway app services — railway up from a local checkout is the deploy.
  • Swagger spec once 500'd on UsersController.UploadAvatar; fixed by dropping the redundant [FromForm] and adding [Consumes("multipart/form-data")] — the pattern to copy for any future single-file upload action.
